## 1. Ziel & Abnahmekriterien

ZIEL:
Der ZUGFeRD-Export erzeugt ab sofort ein ECHTES, maschinenlesbares Hybrid-
Rechnungsdokument nach ZUGFeRD 2.x / Factur-X (technisch identisch seit 2.1/1.0):
ein PDF/A-3 (ISO 19005-3), in das die CII-Rechnungs-XML (EN 16931) als Embedded
File `factur-x.xml` mit korrekter AFRelationship und korrekten XMP-Metadaten
eingebettet ist. Die bisherige Mock-Lösung (Textdatei mit "%PDF"-Präfix) wird
komplett ersetzt.

ABNAHMEKRITERIEN (messbar):
1. Der Export über den Rechnungs-Editor (Format "ZUGFERD") und über die
   Schnell-Download-Buttons im Dashboard liefert eine Datei mit gültigem
   PDF-Header `%PDF-1.7` und gültiger EOF-Markierung (`%%EOF`) - keine
   Mock-Textdateien mehr.
2. Das PDF enthält einen Dokument-Katalog-Eintrag `/AF` (Associated Files),
   der auf das FileSpec-Dictionary der eingebetteten `factur-x.xml` zeigt.
3. Das FileSpec-Dictionary enthält `/AFRelationship /Alternative`,
   `/Type /Filespec`, `/UF (factur-x.xml)` sowie `/Desc`.
4. Die XML ist zusätzlich im Namensbaum `/Names /EmbeddedFiles` verzeichnet,
   damit auch Viewer ohne AF-Unterstützung sie extrahieren können.
5. Das XMP-Metadaten-Paket des PDFs enthält:
   - `pdfaid:part = 3` (+ `pdfaid:conformance`, Ziel: B oder U)
   - `fx:DocumentType = INVOICE`
   - `fx:DocumentFileName = factur-x.xml`
   - `fx:Version = 1.0`
   - `fx:ConformanceLevel = EN 16931`
   - die zwingend erforderliche PDF/A Extension-Schema-Deklaration
     (pdfaExtension:schemas) für den fx-Namespace
     `urn:factur-x:pdfa:CrossIndustryDocument:invoice:1p0#`.
6. Das PDF enthält einen OutputIntent mit eingebettetem sRGB-ICC-Profil.
7. Die eingebettete XML ist dieselbe CII-Struktur, die EInvoiceEngine erzeugt;
   der Guideline-URN entspricht dem gewählten Profil (siehe Schritt 3).
8. `npm test` läuft grün; neue Unit-Tests prüfen die Strukturmerkmale 2-7
   automatisiert am erzeugten Binär-PDF (ohne VeraPDF).
9. Ein manuell durchgeführter VeraPDF-Run (PDF/A-3b) + Mustang-Validator/
   KoSIT-Check ist dokumentiert; bekannte Restrisiken sind benannt (Kap. 8).
10. GoBD: Der Export-Vorgang erzeugt einen Audit-Log-Eintrag (audit_logs),
    bestehende Hashkette wird nicht gebrochen.

NICHT-ZIEL (Scope-Grenze):
- Vollständige semantische EN-16931-Feldabdeckung der CII-XML (Adressen,
  Kontakte, Steueraufschlüsselung je Satz) -> gehört zu F6 Validierung.
- Digitale Signatur des PDFs.
- Empfang/Import von ZUGFeRD-Dateien.

## 3. ZUGFeRD-Technische Anforderungen (PDF/A-3, AFRelationship, XMP, Namensbaum, ICC)

3.1 Container: PDF/A-3 (ISO 19005-3)
    * Das visuelle PDF MUSS konform zu PDF/A-3 sein (Level a, b oder u erlaubt;
      realistisch anpeilbar: PDF/A-3b bzw. 3u).
    * PDF-Version im Header: %PDF-1.7 (PDF/A-2/3 basieren auf PDF 1.7).
    * Pflichtmerkmale von PDF/A (relevant für uns):
      - Alle Fonts eingebettet (Subset reicht) -> Chromium/printToPDF bettet
        Fonts standardmäßig ein (erfüllt i.d.R. automatisch).
      - Eingebettetes OutputIntent-ICC-Profil; DeviceRGB-Farben brauchen ein
        sRGB-OutputIntent.
      - XMP-Metadaten mit pdfaid:part/pdfaid:conformance.
      - Dokument-/ID im Trailer/Katalog.
      - Keine Verschlüsselung, kein JavaScript, keine Notation-Annotationen.
      - XMP muss UNkomprimiert als /Metadata-Stream vorliegen.

3.2 Attachment (das Herzstück):
    * Genau EINE Invoice-XML als Embedded File auf DOKUMENT-Ebene:
      - Katalog: `/AF [ <filespec-ref> ]` (Associated Files, neu in PDF/A-3).
      - FileSpec: `/Type /Filespec /F (factur-x.xml) /UF (factur-x.xml)`
        `/Desc (...) /AFRelationship /Alternative`
        `/EF << /F <embeddedfile-ref> /UF <embeddedfile-ref> >>`
      - EmbeddedFile-Stream: `/Subtype /text#2Fxml` (MIME text/xml),
        `/Params << /Size n /ModDate (D:...) >>`.
    * Dateiname PFLICHT (Fixnamen!):
      - ZUGFeRD 2.1+/Factur-X (Profil EN 16931/BASIC/EXTENDED): `factur-x.xml`
      - Ausnahme Referenzprofil XRECHNUNG: `xrechnung.xml`
    * AFRelationship-Wert - WICHTIGE NUANCE (honest):
      - Für ZUGFeRD/Factur-X in DEUTSCHLAND mit Profil EN 16931 ist
        `/Alternative` vorgeschrieben (XML und PDF sind zwei gleichwertige
        Darstellungen desselben Inhalts).
      - `/Source` wäre zulässig, wenn das PDF aus der XML erzeugt wurde und
        der Empfänger außerhalb Deutschlands sitzt (Factur-X-Regel).
      - `/Data` taucht in frühen Factur-X-1.0-Beispielen auf und wird teils
        von Tools akzeptiert, ist aber laut aktueller Spezifikation für
        EN 16931 nicht der empfohlene Wert. ENTSCHEIDUNG: Wir setzen
        `/Alternative` (sicherster, in DE akzeptierter Wert).
    * Zusätzlich MUSS die XML im klassischen Namensbaum hängen:
      `/Names << /EmbeddedFiles << /Names [ (factur-x.xml) <filespec-ref> ] >> >>`
      (Kompatibilität mit Viewern/Tools ohne AF-Support).

3.3 XMP-Metadaten (exakte Felder):
    * PDF/A-Identification: `pdfaid:part=3`, `pdfaid:conformance=B|U`.
    * Basis (dc, xmp, pdf): dc:title/dc:creator optional sinnvoll,
      pdf:Producer, xmp:CreatorTool, dc:format="application/pdf".
    * Factur-X/ZUGFeRD-Extension (Namespace
      `urn:factur-x:pdfa:CrossIndustryDocument:invoice:1p0#`, Prefix `fx`):
      - fx:DocumentType       = INVOICE            (immer)
      - fx:DocumentFileName   = factur-x.xml       (MUSS zum Attachment-Namen passen!)
      - fx:Version            = 1.0                (ZUGFeRD 2.1+ = Factur-X 1.0)
      - fx:ConformanceLevel   = EN 16931           (oder BASIC/XRECHNUNG ...)
    * KRITISCH (häufigster VeraPDF-Fehler): Die vier fx:-Properties sind KEINE
      vordefinierten XMP-Schemata. PDF/A verlangt ISO 19005-3, Clause 6.6.2.3.1,
      eine Extension-Schema-Deklaration:
      pdfaExtension:schemas -> rdf:Bag ->
        pdfaSchema:schema       = "Factur-X PDFA Extension Schema"
        pdfaSchema:namespaceURI = urn:factur-x:pdfa:CrossIndustryDocument:invoice:1p0#
        pdfaSchema:prefix       = fx
        pdfaProperty[] für DocumentType (external), DocumentFileName (external),
        Version (external), ConformanceLevel (external) mit value-type Text.
    * XMP-Paket: `<?xpacket ...?>`-Wrapper, unkomprimierter Stream im Katalog
      unter /Metadata.

3.4 OutputIntent / ICC:
    * Katalog: `/OutputIntents [ << /Type /OutputIntent /S /GTS_PDFA1
      /DestOutputProfile <icc-stream-ref> /OutputConditionIdentifier (sRGB) >> ]`
    * ICC-Profil: sRGB. Woher nehmen (Lizenz beachten)?
      - @cantoo/pdf-lib bringt beim convertToPDFA()/embedFacturX()-Weg ein
        eingebautes sRGB-ICC-Profil MIT (in der Bibliothek gebündelt) ->
        wir müssen KEIN eigenes Profil mitschleppen. (Empfehlung!)
      - Falls Eigenbau-Fallback nötig: frei lizenzierbare Profile wie
        sRGB2014.icc (ICC/color.org, freie Nutzung) oder sRGB-v4-preference -
        NICHT Ghostscript-Profildateien als "Code" behandeln; die reine
        .icc-Binärdatei ist zwar datenseitig unproblematisch, sauberer ist
        die color.org-Variante.

3.5 Konsistenzregeln (werden von Empfängern geprüft):
    * fx:DocumentFileName == tatsächlicher Attachment-Dateiname.
    * fx:ConformanceLevel == Guideline-URN der eingebetteten XML:
      - Profil EN 16931 =>
        urn:cen.eu:en16931:2017 (bzw. streng:
        urn:cen.eu:en16931:2017#conformant#urn:factur-x.eu:1p0:en16931)
      - Aktuell erzeugt einvoice.js aber den XRECHNUNG-URN (:105)! Entweder
        XML-URN je Profil parametrieren (Schritt 3) ODER Profil XRECHNUNG
        deklarieren (dann Filename xrechnung.xml). -> Beides vorgesehen.
    * Beträge in PDF-Sicht vs. XML müssen übereinstimmen (BR-CO-Risiko;
      da beide aus denselben state-Daten generiert werden, gegeben).

## 8. Risiken & Fallbacks

R1  Chromium-Basis-PDF ist nicht 100% PDF/A-streng (Fonts-Subset-Tags,
    Annotation-Flags, Transparenz ist ab PDF/A-2 erlaubt, JPEG2000 verbietet
    Chromium ohnehin).
    -> Wahrscheinlichkeit: mittel; Impact: VeraPDF meldet Details.
    -> Gegenmaßnahme: (a) embedFacturX/convertToPDFA normalisiert Struktur;
       (b) Fallback b: Sichtseite komplett mit @cantoo/pdf-lib selbst zeichnen
       (eingebettete TTF) -> volle Kontrolle; (c) Doku der veraPDF-Befunde +
       ggf. gezielter Fixes (z.B. printToPDF-Optionen: keine Headers/Footers,
       scale 1).

R2  Fork-Risiko @cantoo/pdf-lib (kein Upstream-Hopding): Breaking Changes /
    Einstellung der Pflege.
    -> Lock Version (^2.9.1 pinning in package.json), Adapterlayer nur in
       zugferd-builder.js (eine Datei austauschbar), Fallback b als
       dokumentierter Escape-Hatch (API-Fläche klein: attach+convert).

R3  AFRelationship-Verwirrung (/Alternative vs /Data vs /Source).
    -> Entscheidung fixiert: /Alternative (DE, EN 16931). In Konstante
       AF_RELATIONSHIP im Builder zentral; Kommentar mit Quellenverweis.

R4  Guideline-URN-Mismatch (aktueller Code hart auf XRechnung 2.3,
    einvoice.js:105) vs fx:ConformanceLevel.
    -> Schritt 2 löst das sauber (Profilparameter); Testfall Z5 sichert ab.

R5  Semantische Lücken der CII (fehlende Adressen/Kontakte/Steueraufschlüs-
    selung je USt-Satz) -> Empfänger-Schematron (EN16931-Check) könnte
    meckern, obwohl Container valide ist.
    -> Scope-Kommunikation: F5 = Container; Feldlücken via F6-Validierung/
       Stammdaten-Ausbau. Im UI-Hinweistext "Container-konform, semantische
       Vollständigkeit gemäß Stammdaten".

R6  IPC-Payload-Größe (HTML der Sichtseite bei Schritt 7 > MB-Bereich).
    -> printToPDF im Hidden-Window hält HTML im Main; Transfer Renderer->Main
       nur einmalig; bei sehr großen Belegen: Grenze prüfen, ggf. Template-
       Datei + JSON-Daten senden statt HTML-String.

R7  Windows-Pfad/Lizenzdetails ICC: gebündeltes Profil der Bibliothek
    verwenden; kein Ghostscript-Material committen (AGPL-Hygiene).

R8  Regression im bestehenden save:pdf-Flow.
    -> save:pdf bleibt UNANGETASTET; neuer Kanal parallel; Tests laufen via
       npm test (node --test, package.json:8) komplett ohne Electron.
